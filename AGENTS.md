# Sendrift — mandatory agent and engineering rules

> **Обязательно для любого ИИ-агента, генерирующего/меняющего код.** Конфликт требований: безопасность и корректность → этот документ → `ARCHITECTURE.md` → `CONTEXT.md` → локальные пожелания. Если новое требование сознательно меняет архитектуру, обновить документы в том же изменении.

## 1. Нельзя менять выбранный стек без явного решения

- **Нельзя** заменять PostgreSQL на SQLite (включая тесты, где нужна семантика Postgres).
- **Нельзя** хранить содержимое файлов в PostgreSQL.
- **Нельзя** использовать публичные бакеты или открытые ACL объектов.
- **Нельзя** вводить Redis, Celery, Kafka, Kubernetes, микросервисы, ORM на фронтенде или второй backend «на всякий случай».
- **Нельзя** реализовывать основной backend через Next.js route handlers: Next.js — UI, FastAPI — API.
- **Нельзя** добавлять авторизацию пользователей, платёжки или новые фичи вне MVP без отдельного согласованного изменения.

## 2. Критические запреты по безопасности

- **Никогда** не коммитить `.env`, ключи S3, пароль БД, реальные токены доступа или содержимое пользовательских файлов.
- **Никогда** не писать `share_token`, `manage_token`, presigned URL, содержимое файлов или пароли в access logs, error logs, exception traces, метрики и аналитику. Логи HTTP должны редактировать/маскировать path с токеном, а не просто выключать body logging.
- **Нельзя** генерировать ссылки/секреты через UUID4 в качестве пароля, `random`, timestamp, hash имени файла или автонумерацию. Использовать `secrets.token_urlsafe(32)` либо эквивалент с >= 256 бит криптографической случайности.
- **Нельзя** хранить токены в открытом виде в БД. Хранить `SHA-256` хеш высокоэнтропийного секрета. Секрет управления не должен входить в публичную ссылку.
- **Нельзя** доверять `filename`, MIME type, `Content-Length`, расширению, `X-Forwarded-For` из недоверенного запроса. Размер проверяется на уровне reverse proxy и приложения; IP берётся только из доверенной цепочки proxy.
- **Нельзя** интерпретировать/выполнять содержимое загруженного файла, отдавать его inline или использовать исходное имя как ключ объекта/путь в файловой системе.
- **Нельзя** отдавать прямую вечную ссылку на S3. Для MVP скачивание выполняется только через API с проверкой токена и срока жизни.
- **Нельзя** обещать «end-to-end encryption», «проверен антивирусом», «безопасен от вредоносных файлов», пока это не реализовано и не проверено.
- **Нельзя** публиковать анонимную загрузку в Интернет без проверенных rate limits, квот, мониторинга расходов/трафика и политики реагирования на злоупотребления. Перед публичным запуском отдельно решить вопрос сканирования файлов и процедуры жалоб/удаления.
- **Нельзя** раскрывать внутренние ошибки БД/S3 через HTTP API или наружу стек-трейсы.

## 3. Ограничения и контракты MVP

- Одна ссылка содержит **ровно один** файл, размер строго `1..104857600` байт (100 MiB).
- Разрешённые TTL: `1h`, `24h`, `7d`. Все сроки сравниваются в UTC на сервере.
- TTL начинается от `ready_at` (успешного завершения загрузки), не от выбора файла.
- Перед успехом загрузки API должен удостовериться, что объект сохранён в storage и метаданные перешли в `ready`.
- Секрет управления выдаётся один раз и **не должен** повторно возвращаться по публичной ссылке.
- Метаданные доступны только владельцу действительного share token. Без токена не создавать каталог объектов, индекс или API списка файлов.
- Истёкшую или удалённую ссылку API не обслуживает даже до физической уборки файла.
- Для неизвестных и недоступных ссылок допустим единый нейтральный ответ `404`, чтобы не выдавать состояние ресурса посторонним.
- При ошибке во время загрузки/удаления не заявлять пользователю об успешном завершении.

## 4. Код и структура

- TypeScript `strict: true`, Python с аннотациями типов в публичных интерфейсах.
- Валидация и права доступа **обязательно на сервере**, а не только в браузере.
- Структура FastAPI: `api` (HTTP), `services` (бизнес-логика), `repositories` (Postgres), `storage` (S3 adapter), `models/schemas`, `worker`.
- Роуты не должны содержать реализацию S3/SQL напрямую.
- Миграции через Alembic, запрет `create_all()` как способ управления production DB.
- Конфигурация из окружения с безопасными значениями по умолчанию. Не включать дебаг/открытый CORS в prod.
- HTTP ответные схемы документировать в OpenAPI, не менять контракт молча.
- Прогресс загрузки показывает реальные отправленные байты, а не таймер. Стадия «обработка» отделяется от прогресса передачи.
- Не добавлять глобальный state in-memory для доступа/квот в многопроцессной среде; лимиты должны работать на доверенном edge/общем хранилище.

## 5. Работа с объектами и отказами

- Ключ каждого объекта независим от исходного имени, генерируется на сервере и не переиспользуется.
- При обрыве загрузки, ошибке записи объекта или сбое БД должны быть явно определены компенсация/очистка и способ обнаружить «осиротевшие» объекты.
- Удаление должно быть идемпотентным: повторный запуск не создаёт ошибочных состояний и не восстанавливает доступ.
- Сбой cleanup worker **не** продлевает доступ к просроченным ссылкам.
- Не добавлять одноразовые/лимитированные скачивания на базе одной только S3 presigned URL: подписанная ссылка может использоваться повторно до истечения её срока.
- Отдельно описывать и тестировать конкурентные сценарии: повторный DELETE, истечение срока во время скачивания, прерванная загрузка.

## 6. Обязательные тесты

На каждый функциональный вертикальный срез добавлять автоматические проверки:

- Валидная загрузка и byte-for-byte скачивание.
- Файлы `0`, `1`, `100 MiB`, `100 MiB + 1` байт (большие кейсы в integration/smoke, не в каждом unit-тесте).
- Недопустимый TTL, некорректный токен, истёкшая ссылка.
- Удаление с неправильным/правильным секретом управления.
- Сбой object storage, сбой DB commit, cleanup после аварии.
- Повторный cleanup и отсутствие публичного доступа к бакету.
- Проверка, что страницы и API не выводят секреты в логи.

Для каждого изменения запускать доступные проверки `pytest`, `ruff`, `tsc --noEmit`, lint. Если окружение не позволяет запуск, сказать об этом, а не писать «всё протестировано».

## 7. Запреты на «вайбкодерские» shortcuts

- Никаких фейковых API, моковых состояний или `TODO` за кнопкой, которая визуально выглядит рабочей.
- Никаких `except: pass`, отключения TLS-верификации, `CORS *` в проде, `allow_origins=['*']` с cookies, открытых `/docs`/debug по умолчанию на публичном сервере.
- Никакого удаления тестов ради зелёного CI, отключения строгой типизации или игнорирования ошибок линтера пачками.
- Не переписывать целые модули ради маленького изменения и не придумывать абстракции без реальной необходимости.
- Не добавлять библиотеки только ради визуального эффекта; учитывать стоимость сборки и зависимостей.

## 8. Формат отчёта ИИ после правки

В конце каждой задачи кратко зафиксировать:

1. Что изменено и почему.
2. Какие файлы/контракты затронуты.
3. Какие тесты реально запускались и что получилось.
4. Что осталось непроверенным и какие есть риски.
5. Если принято новое архитектурное решение — где обновлена документация.

**Главный принцип:** лучше меньше проверенного рабочего кода, чем большой набор файлов, который трудно объяснить и невозможно безопасно развернуть.
