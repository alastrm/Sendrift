# Sendrift — project context

> **Назначение:** постоянный контекст для ИИ-помощника или нового участника команды. Здесь описано **что** и **зачем** строим. Запреты и обязательные правила содержатся **только** в `AGENTS.md`, технические решения — в `ARCHITECTURE.md`.

## 1. Идентичность продукта

- **Название:** Sendrift (рабочее).
- **Короткое описание:** временная передача одного файла по ссылке без регистрации.
- **Слоган:** Share files. Leave no clutter.
- **Целевой пользователь:** человек, которому нужно быстро передать документ, архив, изображение или другой файл без регистрации, переписок и настройки папок.
- **Главная ценность:** прозрачный жизненный цикл файла, простой интерфейс и честные ограничения.

## 2. Основные сценарии

### Отправитель

1. Открывает главную страницу.
2. Перетаскивает **один** файл или выбирает его вручную.
3. Выбирает срок: 1 час, 24 часа или 7 дней.
4. Видит реальный прогресс и результат (успешно / ошибка).
5. Получает ссылку; копирует её в один клик.
6. Получает отдельную возможность удалить собственный файл досрочно через секрет управления. Секрет не включается в публичную ссылку.

### Получатель

1. Открывает ссылку.
2. Видит минимум нужного: название файла, размер и время истечения.
3. Нажимает «Скачать» и получает файл.
4. При недоступной/удалённой/истёкшей ссылке видит понятную нейтральную ошибку.

## 3. Границы MVP

**Входит:** одна загрузка = один файл = одна ссылка; анонимные отправитель и получатель; серверная проверка срока; ограничение 100 MiB; логичное состояние upload/download/error; реальное удаление по расписанию; ручное удаление при знании секрета управления.

**Не входит:** учётные записи, кабинеты, команды, платежи, интеграции, E2EE, антивирус как уже работающая функция, предпросмотр содержимого, количество скачиваний, одноразовые ссылки, возможность продолжить прерванную загрузку.

**Задача MVP:** показать законченную, тестируемую вертикаль от выбора файла до скачивания и физического удаления из storage, а не максимальное количество кнопок.

## 4. UX и визуальное направление

- Минимализм без маркетинговой перегрузки.
- Одна ясная основная задача на экран; крупная зона загрузки.
- Светлая и тёмная темы допустимы, но не должны блокировать MVP.
- Состояния: idle, dragging, validating, uploading, success, error; для страницы скачивания: loading, available, unavailable, download-started/error.
- Адаптивность для телефона и десктопа, доступность клавиатурой.
- Не показывать фальшивые проценты, фальшивую статистику или недействующие кнопки.
- Сообщения об ошибках короткие, без секретов и без внутренних деталей API.

## 5. Нефункциональные цели

- **Корректность:** нет выдачи ссылки до подтверждения сохранения объекта; доступ после истечения блокируется независимо от того, успел ли worker удалить объект.
- **Предсказуемость:** срок жизни отсчитывается от завершения успешной загрузки.
- **Безопасность:** закрытое хранилище, случайные секреты, проверка прав на сервере, нейтральная обработка несуществующих ссылок.
- **Экономность:** без постоянных очередей и лишних сервисов на первом этапе.
- **Объяснимость:** разработчик способен объяснить поток данных, обработку отказов и ограничения.
- **Воспроизводимость:** установка через Compose и миграции, автоматизированные тесты.

## 6. Как мы работаем с ИИ

ИИ ускоряет реализацию, но не принимает продуктовые и архитектурные решения самовольно.

При новой задаче помощник должен:

1. Свериться с `AGENTS.md` и `ARCHITECTURE.md`.
2. Определить конкретную вертикаль задачи: UI → API → DB/storage → тесты.
3. Указать затрагиваемые файлы и риски, если изменение нетривиально.
4. Реализовать минимальное связное решение без преждевременных абстракций.
5. Проверить тесты/типизацию, честно описать, что не проверено.
6. При необходимости обновить техническую документацию.

Не считать сгенерированный код автоматически проверенным. Не расширять MVP без осознанного решения.

## 7. Определение «готово» для MVP

Сценарий: пользователь загружает реальный файл (например, 20 MiB), получает действительную ссылку, другой браузер скачивает файл с идентичными байтами; после истечения срока сервер немедленно отказывает, а worker физически удаляет объект; пользователь может удалить файл досрочно. Все эти шаги подтверждены тестами или воспроизводимыми ручными проверками.

## 8. Открытые вопросы после MVP

- Нужно ли постоянное хранение метаданных для статистики?
- Какие география, стоимость трафика и политика обработки жалоб будут у публичного сервиса?
- Когда выгоднее переходить на presigned upload и multipart upload?
- Нужны ли пользовательские аккаунты вообще?

Эти вопросы **не** следует автоматически превращать в новые задачи текущего MVP.
